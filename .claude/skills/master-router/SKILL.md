# master-router — 거장 스킬 추천 라우터

> mimesis 레포의 메타 스킬. 거장(figure) 스킬이 늘어날수록 description 표면이 겹쳐 자동 호출이 흐려진다. 이 스킬은 (1) 사용자 상황을 짧게 진단하고 (2) 매칭되는 거장 스킬 후보를 그 인물이 왜 이 상황에 맞는지와 함께 보여준 뒤 (3) 사용자가 직접 명시 호출하도록 안내한다.

## When to use

- 호출되어야 하는 상황:
  - 사용자가 "어떤 스킬 / 어느 사고법 / 거장 추천" 류 질문을 던질 때.
  - 사용자의 작업이 거장 스킬 영역(깊은 사고·진단·재정의·구조화·자세 점검)에 분명히 걸리지만, 어느 인물·개념도 명시하지 않아 단일 figure 스킬로 자동 매핑되지 않을 때.
  - 두 개 이상의 figure 스킬 트리거 표면에 동시에 걸려 자동 호출이 충돌할 가능성이 있는 상황 (예: 학습 진척 호소가 fromm/lee-eo-ryeong 둘 다에 걸리는 경우).
- 호출하지 말 것:
  - 사용자가 이미 거장명("프롬", "이어령", "맥킨지" 등)이나 figure 스킬의 고유 개념("having mode", "MECE", "정문(正問)")을 명시적으로 부른 경우 — 그 스킬이 직접 호출되어야 한다.
  - 거장 스킬과 무관한 작업: 코드 작성·실행·검색·조회·간단한 사실 질문·이미 답이 있는 실행 과제.
  - 단일 figure 스킬에 자명하게 떨어지는 경우 — 라우터는 ambiguity를 해소하기 위해 있다, 매핑이 명확하면 건너뛴다.

## The procedure
사용자 입력 앞에서 이 순서로 머리를 굴린다.

1. **자동 매핑 가능성을 먼저 검토한다.** 사용자가 명시한 인물명/고유 개념/명백한 트리거 문구가 있으면, 이 스킬은 즉시 빠지고 해당 figure 스킬을 직접 호출하도록 안내한다. **Why:** 라우터는 ambiguity 해소 장치다. 명확한 호출에 끼어들면 한 단계의 마찰만 더한다.

2. **사용 가능한 거장 스킬 목록과 description을 한 번 훑는다.** 현재 레포의 `.claude/skills/<figure-name>/SKILL.md` 중 figure-anchored 스킬만 후보 풀로 본다 (라우터 자신과 인프라 스킬은 제외). **Why:** 후보 풀이 정의되어야 추천이 deterministic 해진다. "기억에 있는 거장"으로 추천하면 환각이 들어온다.

3. **사용자 컨텍스트를 3축으로 진단한다 — 활동·기준·신호.**
   - **활동**: 사용자가 지금 무엇을 하고 있는가? (학습/카피/문제정의/자기소개/관계/구매/회의/축적)
   - **기준**: 사용자가 무엇이 늘면/달라지면 성공이라 보고 있는가? (양 vs 깊이 / 정답 vs 정문 / 분석 vs 행동)
   - **신호 단어**: 사용자 문장에 어떤 명사·관용어·동사가 박혀 있는가? ("다 못 읽었어", "당연한 거 아닌가", "MECE", "스펙" 등)
   
   **Why:** 거장 스킬은 인물 고유 어휘·기준·진단축으로 구별된다. 이 3축에 매핑하면 후보가 자연스럽게 좁아진다.

4. **컨텍스트가 부족하면 1~3개의 좁은 질문을 던진다.** AskUserQuestion으로 단일 선택지 형태로 묻는다. 질문은 모두 "활동/기준/신호" 축 중 하나를 좁히는 것이어야 한다 — 일반적인 "어떤 도움 드릴까요" 같은 질문은 금지. **Why:** 사용자 시간이 한정돼 있다. 4개 이상 묻거나 광범위한 질문을 던지면 라우터를 쓰는 비용이 figure 스킬을 직접 호출하는 비용을 넘는다.

5. **매칭되는 거장 스킬 1~3개를 후보로 뽑는다.** 각 후보에 대해:
   - **인물 + 스킬명** (사용자가 호출에 쓸 정확한 이름).
   - **이 상황에 왜 맞는가** — 사용자 문장의 어떤 신호/기준/활동이 이 거장의 어떤 mental move와 맞물리는지 1~2 문장으로.
   - **호출 트리거 예시** — 사용자가 다음 turn에 어떤 식으로 말하면 그 figure 스킬이 자동 호출되는지 1~2 문장.
   
   **Why:** 후보를 그냥 던지면 라우터가 "디렉토리 listing"이 된다. "왜 이 인물이 이 상황의 거울인가"가 같이 와야 사용자가 figure-situation 매핑을 학습하고, 다음에는 라우터를 거치지 않고 직접 호출할 수 있게 된다.

6. **자동 호출하지 않는다 — 사용자에게 명시 호출을 넘긴다.** 추천 후 라우터는 거기서 멈춘다. 사용자가 다음 turn에 그 스킬명을 부르거나 트리거 문구를 쓰면 그때 figure 스킬이 발화된다. **Why:** README 권장 흐름과 정합. 자동 호출하면 라우터가 또 하나의 "결정을 대신 내리는 층"이 되어, 거장 사고를 자기 것으로 만들겠다는 mimesis의 본래 의도를 흐린다 — 어떤 거장이 이 상황에 맞는지 의식적으로 고르는 한 박자가 학습 그 자체다.

7. **후보가 0개면 솔직히 그렇게 말한다.** 매칭되는 거장 스킬이 없으면 "지금 상황은 현재 레포의 거장 스킬 범위 밖이다"라고 말하고, 어떤 카테고리의 거장이 추가되면 좋을지 1줄로 제안한다 (로스터 확장 입력). **Why:** 억지 매칭이 가장 큰 실패 모드. 후보를 만들기 위해 figure 스킬을 왜곡하면 그 스킬의 description 표면이 또 흐려진다.

## Heuristics

- **사용자가 인물명을 한 단어라도 명시했다 → 라우터는 빠진다.** "프롬", "이어령", "맥킨지"가 들어오면 직접 호출. **Why:** 명시 호출은 ambiguity가 이미 해소된 상태. 라우터가 끼면 마찰만 늘어난다.
- **후보가 4개 이상이 되면 진단이 부족한 거다 — step 3으로 돌아간다.** **Why:** 후보가 많다는 건 사용자 상황이 아직 좁혀지지 않았다는 신호. 추천은 1~3개여야 사용자가 선택 부담 없이 다음으로 넘어간다.
- **질문은 한 번에 최대 3개까지, 모두 단일 선택지 형태.** **Why:** 라우터의 비용 상한선. 이걸 넘으면 사용자가 도구를 버리고 직접 figure 스킬을 호출하는 게 더 싸진다.
- **figure 스킬의 description을 추천 이유에 그대로 인용하지 않는다 — 사용자 상황의 어떤 문장/신호에 매핑되는지 가공해서 보여준다.** **Why:** description 인용은 "스킬 카탈로그 읽기"고, 매핑은 "이 사용자에게 왜 이 거장인가"의 진단이다. 후자가 라우터의 가치.
- **억지 매칭보다 빈 손이 낫다.** 매칭이 약하면 0개로 반환하고 로스터 확장 제안. **Why:** 한 번의 잘못된 추천이 사용자의 raw skill 신뢰를 깎는다 — 그 이후에는 자동 호출도 명시 호출도 회의하게 된다.
- **추천 후 라우터는 끝이다 — 같은 turn에 figure 스킬을 흉내내지 않는다.** **Why:** 흉내내면 figure 스킬의 고유 procedure가 희석된다. 라우터는 디스패처이지 도구가 아니다.

## Examples

**Example 1 — 단일 거장 명확 매칭:**
- Input (사용자): "이번 분기에 산 책이 12권인데 다 못 읽었어. 노트도 밀려 있고. 어떻게 따라잡지?"
- 진단 (활동/기준/신호):
  - 활동: 학습/독서 진척.
  - 기준: 권수·노트 양으로 진척 측정.
  - 신호: "다 못 읽었어", "밀려 있고", "따라잡지" — 모두 양적 축적·따라잡기 프레임.
- 후보 (1개):
  - **erich-fromm-having-vs-being** — 이 상황은 정확히 having mode의 학습 진척 호소다. 권수·노트가 성공 기준이 되어 있고("양이 늘면 성공"), 활동의 결과가 "내가 어떻게 달라졌는가"가 아니라 "얼마나 따라잡았는가"로 측정되고 있다. 프롬의 진단축이 1:1 매핑.
  - 다음 turn 호출 예시: "프롬 진단 좀 해줘" 또는 "이거 having mode 같은데 풀어줘".
- 결정: 1개로 충분하므로 라우터는 여기서 멈춘다. 사용자가 직접 호출.

**Example 2 — 두 거장 표면 충돌, 질문으로 해소:**
- Input (사용자): "스타트업 컨퍼런스 키노트 도입부 만들어야 하는데 진짜 막막해. 다들 'AI 시대의 일' 이런 식으로 시작하는데 너무 진부하지 않아?"
- 진단:
  - 활동: 키노트 도입(글/카피 + 합의된 통설 위에서 새 의미 짓기).
  - 기준: "진부함을 벗어남" — 사전적 정답이 아니라 다른 결의 답이 필요.
  - 신호: "다들 이런 식", "진부하지 않아?" — 통설을 의심하는 입구 + 발산이 필요한 상황.
- 후보 충돌: `lee-eo-ryeong-questioning` (통설 의심·정문) vs `mckinsey-structured-problem-solving` (모호한 문제 구조화)?
- 명료화 질문 (AskUserQuestion 1개):
  > "지금 더 필요한 건 어느 쪽이야?"
  > - 통설을 한 번 뒤집어 도입 한 줄을 새로 짓기 (lee-eo-ryeong)
  > - 키노트 메시지 구조 전체를 MECE로 짜기 (mckinsey)
- 사용자 선택 후 후보 1개로 좁힘. 직접 호출 안내.

**Example 3 — 매칭 0개:**
- Input: "Next.js 14에서 server action 캐시가 갱신이 안 되는데 어떻게 디버깅하지?"
- 진단: 거장 스킬 영역 밖. 코드/디버깅.
- 결정: "현재 레포의 거장 스킬은 깊은 사고·자세·구조화 영역만 다뤄서 이 상황에는 매칭되는 스킬이 없어. 일반 코드 작업으로 진행해. (라이브러리별 디버깅 휴리스틱을 모은 거장이 로스터에 들어오면 보강 가능 — Linus Torvalds 같은 후보.)"

## Anti-patterns (피할 것)

- **자동으로 figure 스킬을 호출하기.** 추천 후 같은 turn에 그 스킬을 실행. **Why:** README 권장 흐름 위반. 자동 호출하면 사용자가 figure-situation 매핑을 학습할 기회가 사라지고, 라우터가 결정을 가로채는 또 하나의 층이 된다.
- **3개를 초과하는 후보 나열.** "후보가 5개 있는데 다 좋아 보여요" 식. **Why:** 진단이 부족하다는 신호. 4개 이상이면 step 3으로 돌아가서 활동/기준/신호 중 하나를 더 좁혀야 한다.
- **figure 스킬 description을 그대로 복사한 이유.** "이 스킬은 X를 다룹니다" 같이 카탈로그 글을 옮겨오기. **Why:** 매핑이 아니라 listing. 사용자 문장의 어떤 신호와 어떻게 맞물리는지가 가공돼야 한다.
- **억지 매칭으로 후보 만들기.** 매칭이 약한데도 0이 부끄러워 1개를 내미는 것. **Why:** 잘못된 한 번의 추천이 raw 스킬에 대한 신뢰를 깎는다. 빈 손이 낫다.
- **라우터 안에서 figure 스킬을 흉내내기.** "프롬이 맞을 것 같은데 우선 having mode 진단을 해볼게요" 식. **Why:** 디스패처가 도구를 흉내내면 figure 스킬의 고유 procedure가 희석된다. 라우터는 추천에서 끝.
- **사용자가 이미 인물명을 부른 자리에 끼어들기.** "맥킨지 방식으로 풀어줘"에 라우터가 먼저 답하기. **Why:** 명시 호출은 ambiguity가 이미 해소된 상태. 마찰만 추가하고 신뢰를 깎는다.

## Output expected

이 스킬을 통과한 산출물은 다음 3블록을 포함한다:

1. **진단 (3~5줄)** — 사용자 입력에서 짚은 활동·기준·신호 단어. 어떤 거장 영역에 걸리는지 한 줄로.
2. **후보 (1~3개)** — 각 후보마다:
   - 스킬명 (사용자가 호출에 쓸 정확한 이름).
   - 이 상황에 왜 맞는가 (사용자 문장 → 거장 mental move 매핑, 1~2 문장).
   - 다음 turn에 어떻게 호출하면 되는지 (트리거 문구 예시 1~2개).
3. **다음 행동** — "○○로 다음 turn에 말하면 그 스킬이 발화돼" 한 줄. 후보가 1개면 그것, 2~3개면 사용자가 고르도록.

산출물에 figure 스킬의 procedure·heuristic·example을 미리 풀어 쓰지 않는다 — 그건 그 스킬이 호출됐을 때 발화하는 영역이다.
